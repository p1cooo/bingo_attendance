# Coach rollout baseline: dependency map and release gates

## Data flow audited

`students` and `memberships` retain stable student IDs and enrollment links. Each membership points to one `schedule`, which points to a class and coach. The new `studentPauses` collection keys a dated pause to a membership. An `_student_pause_locks/<membership id>` transaction document serializes interval creation and resumption. The Firestore `_academy_state` snapshots and local `database_state.json` cache now include pauses. Existing `memberships.status = PAUSED` remains a legacy enrollment state and is not interpreted as a dated pause.

Recurring schedules produce `sessions`; occurrence overrides, replacement coaches, cancellations, and planned off days live on those session documents. The session roster keeps dated-paused students visible, with no attendance requirement. Attendance writes reject a mark on a paused enrollment. Historical marks made before a retroactive declaration stay in place and the pause records their IDs for review.

Finance uses `studentFees` as standard fee versions, `studentPayments` as allocated transactions, and `studentAdjustments` as credits or waivers. There is no separate charge or outstanding-balance collection: `server/finance.ts` derives monthly charges and balances. Full-month class pauses produce RM0 for that membership. Partial-month pauses produce a Pending Finance Review line until an Admin enters a custom amount for that membership and month. Other memberships remain billable. The application has no separate accountant role; Admin and Super Admin retain Finance access. Coaches cannot write fees, payments, adjustments, or pause billing reviews.

Attendance marks can generate `replacementCredits`, `replacementAdvanceCommitments`, outbound notification history, and Bingo Space awards. Bingo Space keeps its own `stars_transactions` keyed by `attendance_event_id`, and an award is idempotent. Trial and BOOKED rows carry operational relationships. No reset may delete these links or assume a Firestore attendance change reverses a Bingo Space award.

## Go-live boundary

`ACADEMY_GO_LIVE_DATE=2026-10-01` is the intended Finance billing baseline after an approved test-data reset. It must be the first day of a month. `ACADEMY_ATTENDANCE_GO_LIVE_DATE=YYYY-MM-DD` is a separate, optional official electronic attendance start date. Its exact October 2026 value requires owner approval and is deliberately unset in source. Once the Finance baseline is configured, an unset attendance date keeps roll-call closed; before a configured attendance date, scheduled occurrences remain in place, but roll-call writes and overdue attendance tasks are disabled. From the attendance date onward, ordinary active-session roll call resumes. If neither setting is configured, the previous attendance behavior remains for compatibility. The accountant export omits pre-attendance-start marks. Neither date deletes test data.

October monthly group tuition remains tied to the fee version and enrollment, including dates before electronic attendance starts. For per-session billing, a missing pre-start mark cannot establish whether a lesson was delivered. Finance lists the affected occurrence dates and marks the balance Pending Finance Review; it does not silently charge or waive those lessons. The owner must approve a source of truth or a manual charge policy for those lessons before October balances are final. Pauses, cancellations, off days, and replacement lessons still follow their existing class-specific rules. Do not enable billing on production while historical test transactions remain without reconciling them; otherwise balances may be misleading.

## Reset scope and dry run

Run the read-only inventory with explicit target and date:

`npx tsx scripts/attendanceResetPreflight.ts --project=PROJECT --database=NAMED_DATABASE --environment=production --billing-baseline-date=2026-10-01`

Add `--attendance-go-live-date=YYYY-MM-DD` only after that date is approved. Add `--test-transaction-cutoff-date=YYYY-MM-DD` only after Finance has identified an evidence-backed test transaction cutoff; the billing baseline is never a deletion cutoff. The script validates identifiers against runtime configuration and requires the environment flag to match `FIRESTORE_EMULATOR_HOST`. It reports per-collection counts, attendance statuses and months, field and blocker counts, affected students/classes, Finance candidate counts and cents, and protected fee versions. It has no write path. A date alone cannot prove a payment or adjustment is test-only. Standard fee versions are preserved. Any post-cutoff payment or adjustment, unknown field, award, credit, trial link, booking, or ambiguous row is excluded pending specific review.

The previous attendance-only classifier permits only whole-document deletion of isolated REGULAR marks with no protected fields or links. A mixed-purpose attendance row needs a separately reviewed **field-level** operation; no field-level executor exists because a historical award, credit, or booking may depend on `status`, `marked_at`, or the attendance document ID. The safe default is preservation. The exact candidate document IDs and hashes must be recorded in an owner-approved manifest after a live read-only inventory. The executor must use that manifest, compare current hashes in transactions, cap batches, journal completed IDs, and re-check target, date, backup, and write freeze before each batch. `_academy_state` attendance and Finance cache entries plus `_system/academy` revision must be refreshed or invalidated together so cleared test data does not reload. The local cache must be refreshed from canonical Firestore before writes reopen. No production executor is included while those dependencies remain unresolved.

## Backup and recovery gate

No Firestore export or restore has been performed in this development task. Before reset approval, the operator must verify the live Hostinger runtime's project and **named database**, export that complete Firestore database to a restricted location, confirm the export operation completed, record counts and integrity metadata, restore into an isolated target, and compare the restored students, memberships, sessions, pauses, attendance, Finance transactions, credits, audits, and snapshots. A VPS code archive and `database_state.json` are not Firestore backups. Freeze legitimate writes during reset and preserve a journal of any writes after the backup; rollback must reconcile those writes before restoring old state. Keep the write freeze if validation fails.

With authorized Google Cloud credentials, an operator can use `gcloud firestore export gs://BUCKET/PREFIX --database=NAMED_DATABASE --project=PROJECT`, wait for the operation to finish, and inspect its metadata and bucket access. Create an **empty isolated named database**, then rehearse `gcloud firestore import gs://BUCKET/PREFIX/ --database=ISOLATED_DATABASE --project=ISOLATED_PROJECT`; verify document counts and representative relationships after import. Do not import into the live database as a rehearsal. Google's [Firestore export/import instructions](https://docs.cloud.google.com/firestore/native/docs/manage-data/export-import) state that exports can include writes made while the export runs, so quiesce writes for a recovery-consistent baseline and preserve a separate journal of later legitimate writes. The official import command can overwrite existing documents; a rollback plan must account for post-backup writes before any live import.

Deployment and reset are separate approvals. Deployment requires the feature branch SHA, passing tests/build, runtime configuration review, and a Hostinger rollback commit. Reset requires the verified named-database backup/restore, live inventory, exact manifest and field policy, selected go-live date, reconciled ambiguous records, and a maintenance window. Neither approval is granted by this document.
